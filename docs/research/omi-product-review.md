# Omi product and wearable UX review

AURA should borrow Omi's recovery architecture before expanding its AI features. For a first personal wearable, the critical experience is simple: deliberately capture something, know that it was saved, recover it after a disconnect, and find the original evidence behind a note.

Reviewed 2026-09-09 against [BasedHardware/omi at `f42089f53c8010dd971b3702ece05a231c9c0c66`](https://github.com/BasedHardware/omi/tree/f42089f53c8010dd971b3702ece05a231c9c0c66). The local checkout's branch reference matches this commit. This is a static source review of the product documents, selected Flutter services/providers/pages, memory access code, and Python MCP adapter. No upstream scripts, apps, backend services, accounts, devices, or CI workflows were run. **Documented intent**, **observed code**, and **AURA recommendations** are distinguished below; none establish Omi's deployed behavior or qualify AURA hardware for wearing.

**Later A04 checkpoint:** the AURA gaps below describe the reviewed baseline. Stable owner/capture identity across token rotation, retained original source text/segments/method, unknown-time handling and the C archive → local Whisper → portal path have since been implemented and exercised locally. The [current source contract](../a04/portal-provenance.md), [95-test companion verification](../../companion/VERIFICATION.md) and [complete remaining backlog](../a04/software-contract.md) track their present state. Mobile recovery, physical capture, correction/revision promotion and full account lifecycle remain unfinished.

## What transfers well

**Documented intent:** Omi puts capture and preservation ahead of cleverness, treats silent loss and competing sources of truth as product bugs, and describes a capture → understanding → memory → retrieval → action loop. Its design guidance calls for obvious next actions, restrained motion, accessibility, and polish subordinate to reliability. These principles fit AURA's existing deliberate recording gesture and physical microphone disconnect. They do not require copying Omi's palette, continuous capture modes, or service stack. [Product principles, lines 8–24](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/PRODUCT.md#L8-L24); [design context, lines 3–17](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/.impeccable.md#L3-L17).

**Observed implementation:** the mobile code distinguishes transfer phases, assigns recovery events to one coordinator, persists queued backend job identifiers, and carries source/review information on memories. These are more immediately useful to AURA than replicating the entire long-term memory system.

## Seven improvements, in order

### 1. P0 — Make capture, preservation, and processing visibly different

**Omi evidence:** `SyncState` separates downloading, waiting for internet, uploading, and server processing, alongside result pointers, failed-record identity, byte counts, and progress. Connection setup separately retrieves battery state, starts listeners, loads device information, and wakes the transfer coordinator. A Bluetooth connection alone is therefore not the whole recovery operation. [Sync state, lines 4–43](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/models/sync_state.dart#L4-L43); [device provider, lines 604–644](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/providers/device_provider.dart#L604-L644).

**AURA gap:** the [desktop companion](../../companion/README.md) exposes status and verified local files, but there is no mobile home screen that explains the recording's current location and next step. The [portal](../../portal/README.md) begins with text notes; it cannot currently represent the device-to-phone portion of the lifecycle.

**Next change:** use explicit states such as “Recording,” “Saving on pendant,” “Saved on pendant,” “Verified on phone,” “Transcribing locally,” and “Note ready.” Cloud storage is a separate optional state. Show the last confirmed observation time when the pendant is disconnected; do not imply that a stale phone screen proves current recording. The physical privacy switch and actual firmware state remain authoritative. First-run onboarding should end with a short intentional recording, stop/save confirmation, transfer, and local playback.

**Acceptance:** unplug the connection during transfer and disable internet during transcription. The UI must still identify every verified local recording, show the unresolved stage, and avoid calling a recording “lost” merely because a summary is unavailable. A capture acknowledgement must come from the device, not from a button animation.

### 2. P0 — Give mobile reconnection and recovery one owner

**Omi evidence:** `BluetoothReadiness` distinguishes permission failures from adapter state and suppresses repeat guidance after the user dismisses an enable prompt. The device service preserves an existing disconnected transport so higher-level reconnection attempts do not cancel native recovery. `RecordingTransferCoordinator` preserves early wake events, coalesces simultaneous events into serial work, and stops its foreground retry timers when backgrounded. `SyncReconciler` explicitly states that its timer is not OS background execution. [Readiness, lines 82–145](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/devices/bluetooth_readiness.dart#L82-L145); [connection ownership, lines 244–275](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/devices.dart#L244-L275); [coordinator, lines 119–200](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/wals/recording_transfer_coordinator.dart#L119-L200); [foreground limitation, lines 101–115](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/wals/sync_reconciler.dart#L101-L115).

**AURA gap:** [device.py](../../companion/src/aura_companion/device.py) provides request timeouts, partial-file resume, and checksum verification within an explicitly started desktop connection. It does not supply mobile lifecycle ownership or an OS-supported background transport.

**Next change:** introduce one mobile session/recovery controller with injected transport, durable recording inventory, and clock. On foreground resume or device reconnection, re-establish services, read status and committed inventory, then resume verified transfers. Keep Bluetooth permissions, Bluetooth power, pairing, connection, and transfer readiness distinct. Start with honest foreground recovery; add background behavior only after validating the actual iOS/Android implementation on phones.

**Acceptance:** exercise permission denial, Bluetooth off/on, out-of-range return, app suspension, process restart, and simultaneous connectivity/device events. Only one transfer drain may run. Dismissed guidance must not reopen in a loop. Recovery must work without navigating to a particular page.

### 3. P0 — Persist the work queue and keep verified audio through failures

**Omi evidence:** the local-recordings provider persists queued job IDs, leaves files retriable after failed/missing jobs, and isolates transient job-poll failures. The reconciler re-arms scheduling in `finally`, preventing one failed pass from stranding pending work. This inspected batch path also deletes local recordings on completed backend jobs; that retention choice should not be copied automatically. [Upload and queued receipts, lines 198–250](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/providers/local_recordings_provider.dart#L198-L250); [job reconciliation, lines 329–378](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/providers/local_recordings_provider.dart#L329-L378); [failure scheduling, lines 45–98](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/wals/sync_reconciler.dart#L45-L98).

**AURA gap:** [upload.py](../../companion/src/aura_companion/upload.py) derives an audio hash, imposes a timeout, refuses redirects, and requires a stored receipt, but does not persist a processing/upload queue or that receipt. [Portal ingestion](../../portal/convex/notes.ts) namespaces `sourceId` with the upload token ID, so rotating credentials changes deduplication identity. Repeating an upload with the same token is idempotent; retrying the same audio under a new token can create another note.

**Next change:** persist per-record stages and attempt outcomes before adding automatic recovery. Separate immutable recording identity, processing revision, and authentication token. Use an owner-scoped stable recording key on the server so credential rotation does not duplicate captures, while a deliberate summary revision remains possible. For the first wearable, keep local audio and explicit verified device deletion. Never turn a failed explicit upload into an unapproved future cloud upload.

**Acceptance:** kill the app after download publication, after transcription, and after the server stores a note but before the client receives the response. Retrying with the same or a rotated token must produce one recording identity and preserve accessible audio. One failed note must not stop later verified notes from processing. Test queue recovery with cloud upload disabled.

### 4. P1 — Preserve evidence and corrections before inventing a memory graph

**Omi evidence:** the mobile memory model carries `conversationId`, review state, edits, visibility, capture devices, evidence, validity, and supersession. Its current-ledger predicate excludes deleted, invalidated, superseded, or negatively reviewed entries. The promotion document specifies a considerably larger atomic graph/receipt architecture; this review treats that as a documented contract, not proof that every producer implements it. [Memory model, lines 66–99](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/backend/schema/memory.dart#L66-L99); [current-state predicate, lines 137–145](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/backend/schema/memory.dart#L137-L145); [promotion contract, lines 3–9](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/memory-promotion-authority.md#L3-L9).

**AURA gap:** local [notes.py](../../companion/src/aura_companion/notes.py) retains segment timestamps and a summary-method label, but [upload.py](../../companion/src/aura_companion/upload.py) sends flattened text without those fields. The [portal schema](../../portal/convex/schema.ts) lacks source spans and revision history; edits patch the current note in place.

**Next change:** carry capture identity/time confidence, transcript segments, processing model/method, and summary revision into the portal. Allow a summary bullet to open its supporting transcript span and local audio when available. Keep the captured transcript distinct from corrected text. Treat enduring facts as explicitly selected notes initially; defer automatic long-term promotion and graph consolidation.

**Acceptance:** edit an incorrect name and regenerate a summary. The original transcript, correction, and processing method remain inspectable; old contradictory text stops entering context. Unknown capture time must remain visibly unknown rather than silently becoming upload time.

### 5. P1 — Make retrieval consent current, revocable, and useful beyond recent notes

**Omi evidence:** `hydrate_and_filter_vector_hits` treats search hits as candidates, rejects missing or stale authoritative items, then applies current access policy before returning content. This is an inspected gateway function, not evidence that every deployed endpoint calls it. [Hydration and freshness, lines 67–130](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/backend/models/memory_search_gateway.py#L67-L130); [access filtering, lines 227–248](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/backend/models/memory_search_gateway.py#L227-L248).

**AURA foundation and gap:** [liveContext](../../portal/convex/notes.ts) already filters by owner, current context consent, and archive state. Its MCP tool returns up to 20 recent eligible notes; it is not query-based retrieval across the entire archive. [The HTTP adapter](../../portal/convex/http.ts) separates context credentials from ingestion and labels captured text as untrusted data. The [portal README](../../portal/README.md) explicitly lists absent account deletion and password recovery.

**Next change:** preserve these narrower permissions. Add owner-scoped search with source links and explicit result/truncation information, then add true deletion and correction invalidation. If embeddings are introduced, re-check authoritative ownership, consent, revision, and deletion on every read. A simple database query is sufficient initially; vectors are optional. Account recovery and deletion need clear supported flows before relying on the portal as a personal archive.

**Acceptance:** revoke context consent, archive/delete a note, or rotate/revoke a token while a search result is cached. The next read must exclude the content. A copied/exported context pack already delivered to another service cannot be retroactively recalled; the interface must distinguish that from future-read revocation.

### 6. P1 — Keep suggested actions visibly reviewable

**Omi evidence:** the task invariant is deliberately conditional. Desktop/proactive capture proposes candidates for a review surface, but clients without that surface use a conservative extractor that can write admitted tasks directly. It also excludes manual/chat/MCP writers from that restriction. It would be inaccurate to describe Omi as universally requiring approval for every extracted task. [Task contract and exceptions, lines 1–31](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/task-capture-suggestion-only.md#L1-L31).

**AURA gap:** the existing extractive/local-model pipeline supplies draft action strings, and the portal stores them as strings. There is no per-action decision record, source span, or approved-task lifecycle.

**Next change:** keep a small review surface inside each note: edit, accept, or dismiss a proposed action, linked to the supporting statement. Do not dispatch reminders, messages, or external tasks automatically. Introduce integrations only after this review loop works; absence of the review surface should leave drafts inert.

**Acceptance:** quoted requests, speculative plans, and transcript prompt injection remain source text. Dismissing one suggestion must not change another. An accepted action has a recorded user decision and traceable source; retrying extraction must not duplicate accepted work.

### 7. P1 — Make storage and recovery a calm daily ritual

**Omi evidence:** the provider refreshes local recordings after disconnect finalization, and the conversation UI has a quiet “not captured” group. That particular group represents scheduled calendar events without recordings, not proven microphone or transport failures. It is a useful presentation example, not an AURA failure detector. [Disconnect handling, lines 526–544](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/providers/device_provider.dart#L526-L544); [capture-gap widget, lines 7–29](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/pages/conversations/widgets/capture_gap_list_item.dart#L7-L29).

**AURA gap:** device status exposes battery voltage, free bytes, privacy state, and recording count, but the user currently reads JSON. The [companion maintenance workflow](../../companion/README.md) requires export, explicit deletion, a physical hold, and potentially lengthy storage erasure. Logical deletion alone does not reclaim the append-only journal.

**Next change:** show remaining storage, last successful save/sync, queued work, and a single relevant recovery action. Explain “deleted but space not reclaimed” clearly. Plan maintenance before the next outing, with power and local-copy checks; keep the existing explicit physical gate. Show raw battery voltage or an explicitly approximate state until a calibrated battery estimate exists. Diagnostic export should contain identifiers, phases, counts, and sanitized error codes, not transcripts or credentials.

**Acceptance:** fill the storage, delete a verified recording, interrupt maintenance, then reconnect. The interface must not promise reclaimed capacity until firmware confirms it. Perform a personal-use day with no network and confirm that capture, local recovery, privacy indication, and the maintenance explanation remain understandable.

## Source issues worth learning from

These observations are bounded to the pinned source. They are not claims of observed user data loss, deployed credential exposure, or a generally broken upstream product.

1. **Lifecycle documentation disagrees with itself.** `PRODUCT.md` says the memory rules remain proposed for a seven-day period, while the registry lists them as locked and explicitly removes that wait. The promotion document itself says “locked” and still contains the old seven-day instruction. AURA should keep one current contract plus executable failure tests, rather than borrowing this process verbatim. [Product status, lines 26–32](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/PRODUCT.md#L26-L32); [registry, lines 19–33](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/README.md#L19-L33); [locked rows, lines 53–58](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/README.md#L53-L58); [promotion document, lines 3–12](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/memory-promotion-authority.md#L3-L12).

2. **A local transcript helper has a replacement crash window.** `LocalSegmentStore.replaceSession` writes a temporary file, deletes the existing destination, then renames the temporary file. Its loader returns an empty list when the destination is absent and does not recover that temporary file. A process exit between deletion and rename can therefore make this helper return no segments despite surviving temporary data. Other audio/WAL recovery may exist; it was not established for this failure path. Use atomic replacement and explicit restart tests in AURA. [Replacement and load, lines 44–72](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/app/lib/services/capture/local_segment_store.dart#L44-L72).

3. **The inspected Python MCP adapter can log secrets/content and block its handler.** The tool schema accepts an optional API key in arguments; the handler logs those arguments at INFO, and `get_memories` logs the full JSON response at INFO. The async handler directly calls synchronous `requests` helpers that supply no request timeout; some helpers also return JSON without checking HTTP status. If INFO logging is enabled, supplied keys and memory contents can enter logs; a stalled request can occupy this adapter's handler. This concerns this stdio adapter, not all Omi MCP/backend paths. AURA should keep credentials in transport configuration, redact diagnostics, use explicit deadlines, and preserve its read-only MCP scope. [Tool schema, lines 84–99](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/mcp/src/mcp_server_omi/server.py#L84-L99); [HTTP helpers, lines 136–184](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/mcp/src/mcp_server_omi/server.py#L136-L184); [async handler and argument log, lines 321–347](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/mcp/src/mcp_server_omi/server.py#L321-L347).

## What to defer or decline

- Defer Omi's full memory graph, autonomous consolidation, many capture transports, and broad integration catalog. Start with one pendant, one recovery owner, durable recordings, and source-linked notes.
- Keep AURA's intentional recording and hardware privacy controls. A missing calendar recording is not an error in a deliberately activated recorder, and “capture the context of your life” must not imply unconsented always-on capture.
- Do not adopt local-audio deletion on cloud transcription completion, automatic task creation on clients without review, or model-visible credential parameters.
- Preserve stable account/recording identity across releases without adopting Omi's particular shared production-data-plane policy. AURA development/test data should remain separate from real personal archives. [Omi's environment-specific contract](https://github.com/BasedHardware/omi/blob/f42089f53c8010dd971b3702ece05a231c9c0c66/product/invariants/data-plane-continuity.md).
- Apply calm, accessible design principles to AURA's own visual identity. An upstream brand rule or a file labelled “locked” is not proof of runtime accessibility, reliability, or enforced behavior.

## Immediate implementation boundary

The implemented companion follow-up separates verified BLE transfer from transcription/refinement/upload, so expensive processing occurs after disconnect and one processing failure does not prevent later saved recordings from being attempted. A disconnect-cleanup failure keeps the WAVs and prevents processing until an explicit retry. An atomic `.sync.json` beside each processed WAV records the last attempted stage and outcome; it contains no transcript, credentials, or raw exception text and schedules no work. It is a recovery hint, not a persisted server receipt or retry outbox. Explicit upload and deletion choices are preserved. See [the CLI](../../companion/src/aura_companion/cli.py) and [its fake-connection tests](../../companion/tests/test_sync.py).

Validation: from `companion/`, `.venv/Scripts/python.exe -m unittest discover -s tests -v` passed all 28 tests, including eight new sync tests. They cover disconnect-before-processing, failures at each processing stage, continuing after a failed download, retaining earlier verified downloads after a later transfer interruption, disconnect failure, capture-in-progress, and explicit upload boundaries. The complete suite also includes checksum/cache/publication tests and a local HTTP test server; it does not connect to a real pendant, model service, or cloud account. This is a desktop reliability improvement, not a mobile app, cloud deployment, or physical-device validation.

The wider recommendations above remain proposed. The first personal-wearable gate is end-to-end capture, interrupted-transfer recovery, local playback, privacy, battery/storage behavior, and a day of actual bench/wear testing; software source review does not replace the separate electrical and assembly qualification holds.
